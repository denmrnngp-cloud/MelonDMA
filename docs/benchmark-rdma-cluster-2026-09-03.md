# RDMA-кластер — замер после Трека A (блокирующий poll)

> **Статус: dev.** Замер 2026-09-03. Сравнение с базлайном `benchmark-rdma-cluster-2026-09-02.md`.
> Харнес тот же: `bench_rdma_cluster.py`, 2 модели × disagg/split × 8 контекстов.
> Сырые данные: `bench_rdma_trackA.csv` (новый) vs `bench_rdma_cluster_results.csv` (базлайн).

## 1. Что изменилось

Одно изменение на стороне llama.cpp (`ggml/src/ggml-rpc/transport.cpp`):

- **`rdma_poll()` переведён с busy-spin на блокирующий poll** через completion-channel:
  `ibv_req_notify_cq` → re-poll → `poll(cc->fd)` → `ibv_get_cq_event`/`ibv_ack_cq_events` → drain → re-arm.
  Два канала (scq/rcq), TCP-control fd в том же `poll()` для детекта мёртвого пира.

Драйверная часть, которая это включила (до этого замера): comp-channel worker
читает смапленный CQE-ринг напрямую (`rdma_cq_pending_local`, ~30 µs wakeup вместо
1 ms kernel-query), плюс фикс токена (24 бит) — см. `docs/Plan.md` §Optimization.

## 2. Итог одной строкой

Busy-poll CPU (главная цель) **упал ~5×**: disagg/rdma `mac_cpu` 48 % → 8.5–10 %
на длинных контекстах. Цена — **TTFT +1–4 %** (латентность пробуждения ~30 µs) и
**prefill −1–4 %** (чуть медленнее bulk-перенос). Bandwidth по decode не потерян.

## 4. Выводы

1. **Трек A работает.** Busy-poll CPU в disagg снят: `mac_cpu` 48.4 → 8.5 % (27B) и
   49.4 → 10.0 % (35B) на 65K — **~5× меньше**, при том же decode tok/s. Это была
   главная накладная (вращающийся `ibv_poll_cq`).
2. **Цена блокировки — задержка.** TTFT +1–4 % на disagg (латентность пробуждения
   comp-channel ~30 µs на комплишен) и prefill −1–4 %. Следующий шаг — direct CQ
   decode (`MELONDMA_DIRECT_CQ=1`, zero-syscall poll) отыгрывает эту дельту.
3. **Split — двояко.** На малых ctx CPU упал (25–30 → 11–21 %), но на больших
   вырос (2–4 → 7–9 %) — блокирующий poll добавил постоянные ~5 % (воркер
   comp-channel + arm/re-arm) там, где спина раньше не было. Split decode при
   этом чуть улучшился (+1–4 %). Регресс убирается адаптивным backoff воркера.
4. **Spark CPU не тронут** (≈100 % в disagg — он и есть prefill-нода).

## 6. Итог после direct + one-sided (замер 2026-09-03, свип RDMA-only)

Все три замера: **base-RDMA (spin)** → **TCP-40GbE** → **RDMA-now**
(direct SQ/RQ + direct CQ decode + one-sided KV WRITE + блокирующий poll).

### 6.1 CPU — busy-poll снят, но до TCP-40G ещё 2.7×

**disagg, macCPU% (27B):**

| ctx | base-RDMA | TCP-40G | RDMA-now |
|---|---|---|---|
| 4096 | 40 | 4.4 | 10.1 |
| 65536 | 48 | 3.3 | 9.1 |

48 → 9 % (было 15× хуже TCP-40G, стало 2.7×). Остаток ~6 % сверх TCP-базлайна —
comp-channel воркер (50 µs poll) + arm/re-arm + `set(local)` memcpy.

### 6.2 Скорость — RDMA паритетен с TCP-40G (TTFT/prefill)

**27B disagg, prefill tok/s:**

| ctx | base-RDMA | TCP-40G | RDMA-now |
|---|---|---|---|
| 32768 | 640 | 644 | 632 |
| 65536 | 548 | 550 | 540 |

TTFT в пределах ±2 % (65K: 137.5 → 137.0 → 139.5). Direct-режим отыграл TTFT,
который блокирующий poll отдавал.

### 6.3 split-decode — RDMA всё ещё проигрывает ~12 % на мелких активациях

**35B split decode tok/s (ctx 1024):** 44.3 (base) → 46.6 (TCP-40G) → 39.9 (now).
Direct-режим разрыв не закрыл — узкое место теперь не poll, а стоимость
post+completion на мелком сообщении.

### 6.4 Сводно

| Метрика | base-RDMA | TCP-40G | RDMA-now |
|---|---|---|---|
| macCPU disagg 65K | 48 % | 3.3 % | **9.1 %** |
| prefill 65K | 548 | 550 | 540 |
| TTFT 65K (s) | 137.5 | 137.0 | 139.5 |
| split decode 35B 1K | 44.3 | 46.6 | 39.9 |

**RDMA больше не проигрывает TCP-40G по скорости/латентности; CPU упал в 5×.**
Остались три задачи: дожать CPU 9→2.5 % (backoff + batch-poll + unsignaled),
убрать `set(local)` memcpy (one-sided в KV-буфер), и split-decode (batch WR +
inline для мелких).
