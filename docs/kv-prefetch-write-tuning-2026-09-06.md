# KV: удаление повторного prefetch и настройка RDMA WRITE

Дата: 2026-09-06; аппаратные ablation начаты 2026-09-05. Область изменений — приватный `/Users/macstudio/llama.cpp`, не DEXT. Продолжение [одного KV batch](kv-transfer-batch-pipeline-2026-09-05.md). Эта итерация реализует два согласованных пункта; не меняет формат/точность KV, CUDA kernels, CQ policy или драйвер.

## 1. Убрать повторное скачивание attention KV

`llama_state_seq_prefetch_ext` вызывался после prefill-чанков. Старый prefetch скачивал attention KV в промежуточный cache, однако final-destination batch обходил этот cache и запрашивал те же данные снова. В режиме `KV_BATCH` с negotiated capability, `WRITE_KV` и `FINAL_DEST` теперь пропускается загрузка, но сохраняется SYNCHRONIZE-барьер очереди и drain ранее начатого prefetch. Число пропущенных участков, байты и время барьера доступны в `GGML_RPC_KV_PREFETCH_SKIP`.

Важная проверка: простое удаление всего вызова было отвергнуто. Оно сокращало TTFT примерно на 75 ms, но увеличивало CPU Mac с ~11% до ~63%. Без прежнего барьера загрузка входов следующего графа может упереться в RQ credits, пока Spark считает, и вызвать активное ожидание SQ. Итоговая реализация оставляет ожидание вычислений без повторной передачи KV. `fence_ms` включает ожидание реального compute и не является чистыми сетевыми накладными расходами.

Возврат старого поведения для A/B: `GGML_RPC_RDMA_KV_PREFETCH=1`. При отсутствии batch capability старый путь сохраняется. Основной batch-протокол по-прежнему opt-in.

## 2. Измерить и настроить WRITE pipeline

SEND/RECV и их negotiated chunk не изменены. WRITE имеет независимые ограниченные параметры:

| Переменная | Допустимые значения |
| --- | --- |
| `GGML_RPC_RDMA_WRITE_CHUNK` | 262144 / 524288 / 1048576 bytes |
| `GGML_RPC_RDMA_WRITE_WINDOW` | 2 / 4 поколения |
| `GGML_RPC_RDMA_WRITE_DEPTH` | 4 / 8 WR на поколение |

Последний WR каждого поколения — signaled; единственный финальный WRITE_WITH_IMM завершает batch. Максимум 32 WR одновременно при SQ depth 64. Слот переиспользуется только после completion соответствующего поколения. Для конфигураций, отличных от прежней 256 KiB × 2 × 8, лениво создаётся отдельный зарегистрированный WRITE ring. Он освобождается после остановки QP; ошибка deregistration не игнорируется.

Добавлен `rdma_write_registered_regions`: тот же production scheduler читает заранее зарегистрированный host source без callback/CUDA/транспортного memcpy. Scoped MR и его владелец удерживаются до окончания операции. Это измерительный путь, а не заявление о NVIDIA GPUDirect.

### Аппаратный ablation: 90 177 280 bytes, 80 участков

Spark → Mac, MTU 4096, один и тот же RC-путь. Raw host: 24 повтора, первые 4 исключены; полная проверка меняющегося pattern и guard bytes. CUDA gate: 44 batch-повтора, первые 4 исключены, дополнительно resize/lifetime и scoped-MR проверки. Все семь окончательных конфигураций прошли без ошибок данных.

| Chunk KiB / windows / WR | Raw server, ms | CUDA gate wall, ms |
| --- | ---: | ---: |
| 256 / 2 / 8 | 53.766 | 60.642 |
| 256 / 4 / 8 | 53.507 | 59.417 |
| 512 / 2 / 8 | 53.234 | 60.300 |
| 512 / 4 / 8 | 53.575 | 58.186 |
| 1024 / 2 / 8 | 53.633 | 59.400 |
| 1024 / 4 / 8 | 53.314 | 58.168 |
| 512 / 4 / 4 | 53.521 | 60.424 |

Raw результат — около 13.4 Gbit/s полезных данных. Разброс порядка 1% не доказывает преимущество большей геометрии для чистого WRITE и не является универсальным пределом Thunderbolt/карты. Raw timer исключает регистрацию, подготовку pattern и проверку; включает production post/completion. CPU Spark в этом тесте включает существующий активный SQ polling.

512 KiB × 4 × 8 — кандидат для итогового профиля: CUDA gate быстрее исходного примерно на 2.46 ms (4.0%), практически равен 1 MiB × 4 при вдвое меньшем отдельном ring (16 вместо 32 MiB). Этот процент относится только к synthetic transfer, не к TTFT. Сквозная приёмка ниже этот кандидат не подтвердила, поэтому дефолтом остались прежние 256 KiB × 2 × 8.

## Сквозная приёмка

Порядок A–B–C–C–B–A; по 2 прогрева и 10 измерений в каждой фазе, всего 20 измерений на вариант. Qwen3.6-35B-A3B, disagg, фиксированные входы (~2180 tokens), 32 выходных токена, Mac host arena 96 MiB. A: старый prefetch, WRITE 256/2/8; B: compute-only prefetch barrier, WRITE 256/2/8; C: тот же barrier, WRITE 512/4/8. Во всех вариантах новый один-batch протокол, не прежние 80 RPC.

Проценты CPU Mac относятся к одному ядру; среднее за запрос включает prefill и decode, это не idle CPU.

Прогон 12:37-12:41, сборка Mac 12:37 с сохранённым барьером. Хеши входов и выходов совпали во всех шести фазах, во всех запросах `one_sided=80`, `fallback=0`.

Разности TTFT с 95% интервалом по Уэлчу: B−A = −4.2 ms ±13.4, C−A = −9.2 ms ±9.4, C−B = −5.0 ms ±14.0. Дрейф между двумя фазами одного варианта (b1 1556.0 против b2 1590.0) больше любой из этих разностей. Подтверждённого выигрыша TTFT нет ни у пропуска, ни у геометрии 512 KiB × 4. Разница 2.46 ms из CUDA gate в TTFT не переносится.

Пропуск снимает 9 вызовов по 2.5 MiB на запрос, около 22.6 MiB повторной передачи, и это не отражается на TTFT. Барьер, заменивший загрузку, ждёт вычисление Spark: в среднем 156.3 ms на вызов при максимуме 342.6 ms, что соответствует prefill-чанку, а не сети. Девять таких ожиданий составляют почти весь TTFT 1.57 s.

### Что зафиксировано

Дефолт WRITE остаётся 256 KiB × 2 × 8 на обеих машинах; 512 KiB × 4 доступен переменными для рабочей нагрузки, которая это измерит. Пропуск повторного скачивания оставлен включённым: он убирает 22.6 MiB лишней передачи на запрос при неизменных TTFT, CPU Mac, CPU Spark и совпадающих хешах вывода.

Первые предварительные прогоны без барьера не принимаются. В самой первой версии счётчика Spark shell quoting давал ложные нулевые CPU deltas; эти нули исключены. Исправленный reader запускает SSH без промежуточной local-shell интерпретации; окончательные данные используют `/proc/PID/stat` и `CLK_TCK`.

## Проверки и ограничения

- Собраны RDMA-варианты Mac и Spark, а также TCP-only RPC library. Mac executable подписан существующими RDMA entitlements.
- Raw gate сначала обнаружил гонку завершения собственного тестового протокола: peer закрывался до получения маленького результата. Добавлен подтверждающий non-inline ACK вне таймера; принимается только полный повторный прогон `kv-next-raw-v2`.
- Генерация данных, guard checking, host-MR registration и ACK не входят в raw transfer timer.
- Активный DEXT 0.396 не пересобирался и не заменялся. Во время измерений основной RPC на 50052 и основной Mac router не перезапускались; тесты использовали отдельные 50053/50054 и 8092. Позже, в 14:14:38 и 14:20:04, основной сервер Spark перезапустился сам (его запускает `start-disagg-cluster.sh`) и сейчас работает со сборкой 12:36, то есть с дефолтом 512 KiB × 4; выбранный дефолт попадёт в него при следующем перезапуске. Основной Mac router по-прежнему работает со своей отдельной сборкой в `build/`.
- После приёмки обе машины приведены к одному исходнику: `ggml-rpc.cpp`, `transport.cpp` и `transport.h` совпадают по sha256. Mac пересобран и подписан 14:19, Spark — 14:29. Прежний файл Spark сохранён как `~/transport.cpp.bak-20260906-1430`. В git ничего не коммитилось.
- `MELONDMA_COMPLETION_POLICY=latency` остаётся условием профиля. Рабочая низколатентная IRQ доставка этим не доказана.
- Destination всё ещё serialized host state, не конечные Metal KV tensors. Внутренние CUDA копии возможны. Изменения wire scheduler не устраняют физическую стоимость передачи 86 MiB.
- Fault injection, reset/unplug и второй Mac в этой итерации не проверялись. Цель 7–15% и превосходство над TCP40 требуют отдельного сопоставимого end-to-end теста.

## Артефакты и воспроизведение

Аппаратные журналы ablation: [kv-next-20260905](../artifacts/kv-next-20260905/); инференс-прогоны приёмки, включая два отклонённых: [kv-next-20260906](../artifacts/kv-next-20260906/). Контрольные порты должны быть свободны перед запуском. Скрипты останавливают только запущенный ими Spark PID, не основной RPC.

Исходный профиль WRITE воспроизводится на Spark переменными `GGML_RPC_RDMA_WRITE_CHUNK=262144`, `GGML_RPC_RDMA_WRITE_WINDOW=2`, `GGML_RPC_RDMA_WRITE_DEPTH=8`; старый prefetch включается на Mac через `GGML_RPC_RDMA_KV_PREFETCH=1`. Для финального A/B используются `kv-optimization-ab.py --out <new-directory> --reps 10` и последующий summarizer с сохранёнными Mac logs. Папка результатов должна быть новой: имена временных Mac logs повторяются, поэтому их следует архивировать перед следующим прогоном.
