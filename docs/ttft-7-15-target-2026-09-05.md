# Цель: сократить сквозной TTFT на 7–15%

Продолжение после согласования пользователя: [реализация одного KV batch, ownership и TX pipeline, результаты gate](kv-transfer-batch-pipeline-2026-09-05.md). Ниже сохранён исходный анализ до этой реализации; формулировки о старом сервере и необходимости согласования относятся к тому моменту.

Дата: 2026-09-05. Это план следующего эксперимента, **не подтверждение достигнутого ускорения**. Анализ использует текущий локальный llama.cpp; код работающего сервера Spark в этой проверке не синхронизировался и не пересобирался.

## База и необходимый выигрыш

- Модель `qwen3.6-35b-a3b`, disagg, RDMA, context_requested=2048, gen=32, mailbox=on.
- TTFT: 1.8805 / 1.8510 / 2.0046 s; среднее **1.9120 s**; errors=0.
- Реальные prompt_tokens: 2197 / 2196 / 2179. Это не три одинаковых входа; такие прогоны недостаточны для строгого небольшого A/B-выигрыша.
- Цель −7%: **1.7782 s**, экономия 133.8 ms.
- Цель −15%: **1.6252 s**, экономия 286.8 ms.
- Приведённые пользователем тёплые `wait_ms=82.923/80.498` дают около 81.7 ms. Даже полное устранение этого интервала — только **4.27%** текущего TTFT. Уже исчезнувшие 27–35 ms регистрации нельзя повторно включать в будущую экономию относительно pagecache-базы.

Чтобы получить 7–15% на этом входе, нужно сократить и другие участки критического пути: prefill, сериализацию/восстановление KV, синхронизации или ещё не учтённые ожидания. Перекрытие сетевого переноса с вычислением само по себе тоже не может сэкономить больше прежней длительности переноса, если больше ничего не меняется.

## Найдено в коде

### 1. Одна MR-область — не один RPC batch

`ggml_backend_rpc_get_tensor_batch()` в `ggml/src/ggml-rpc/ggml-rpc.cpp` при final-destination режиме обходит обычный batch wire path. Он объединяет области регистрации, но затем для каждого тензора вызывает **`submit_rpc_sync(RPC_CMD_GET_TENSOR, ...)`**.

Worker отправляет GET_TENSOR_RDMA и ждёт `rdma_wait_write_imm()` для каждого элемента. Таким образом, `spans=1, one_sided=80` совместим с **80 последовательными request/completion циклами**, а не с одним сетевым KV-запросом.

Первый кандидат: версионированный batch-запрос со списком tensor/offset/size/destination, единым batch ID и ограниченным числом одновременно выполняемых WR. Итоговый notification должен относиться к последней упорядоченной записи того же RC QP; несколько QP требуют явной агрегации завершений. Отдельный error response обязателен — нельзя выдавать частично заполненный batch за готовый.

### 2. На Spark остаётся промежуточная копия

В `rpc_server::get_tensor()` final-destination путь вызывает `ggml_backend_tensor_get(..., chunk.data(), ...)`, затем `socket_t::impl::rdma_write()` копирует эти данные через `memcpy()` в зарегистрированный `tx_buf`.

То есть схема в текущем локальном коде: GPU/backend → temporary chunk → registered TX slot → NIC → destination. Прямой приём на Mac не устраняет автоматически staging на Spark.

Кандидат: выделять ограниченное кольцо зарегистрированных host TX-slots и читать backend сразу в свободный TX-slot, затем отправлять его. Для CUDA отдельно доказать корректность асинхронного чтения в выбранную pinned memory; нельзя заменять это обещанием регистрации любого CUDA-указателя.

### 3. Конвейер ограничен одним вызовом rdma_write

`rdma_write()` уже имеет две staging generations. Но перед возвратом всегда выполняет `drain_pending()`. Поэтому существующий overlap внутри большого вызова не означает overlap между 80 последовательными тензорами или между GPU extraction и передачей следующего тензора.

Кандидат: разделить получение TX-slot, завершение GPU producer, post WRITE и retire WC; держать 2–4 поколения в полёте. Не переиспользовать slot до успешного локального completion. GPU extraction выполнять на существующем backend/CUDA execution context; новый CPU thread без анализа контекстов может ухудшить результат.

### 4. Lifetime destination cache требует усиления

`registered_region` в `transport.cpp` хранит MR, VA, length, число leases и LRU-счётчик, но не владельца allocation или allocation generation. Cache lookup проверяет только попадание VA/length в диапазон. `RPC_RDMA_DEST_STABLE` выставляется по переменной окружения, а не по доказанному ownership-контракту allocation.

Поэтому `reg_ms≈0.012` подтверждает cache hit, но **не доказывает безопасность после освобождения и повторного использования VA**. Перед расширением pipeline нужны persistent arena с удержанием backing allocation, generation/epoch, явное освобождение/invalidation и проверка ошибок deregistration. Также объединять близкие адреса разрешается только внутри известной allocation; небольшой gap между VA сам по себе этого не доказывает.

`MlxRegisteredMetalBuffer` даёт такой ownership-контракт для отдельного shared Metal pool; текущий llama.cpp MR cache автоматически им не становится.

## Измерения до следующей большой правки

1. Проверить идентичность нужных исходников и запущенного сервера Spark; включить серверные `tensor_get_ms` и transport copy/post/wait counters. Не считать наличие строки в локальном исходнике доказательством её выполнения на Spark.
2. Привязать измерения к request/batch ID и фактическому числу элементов. Нынешний серверный агрегат по каждые 80 элементов с глобальными atomic counters не является точным per-request trace при нескольких workers/requests.
3. Снять независимо: prefill GPU, KV export/layout, GPU→host extraction, host memcpy, post, CQ wait, receiver import/layout, первая decode-итерация. Указать пересечения интервалов, не складывать overlapping times как последовательную задержку.
4. Прогнать baseline и каждую оптимизацию чередованием A/B на одинаковых входных токенах, одинаковых GPU clock/power settings, без соседнего инференса. Не меньше 20 измеряемых повторов; cold registration отдельно от warm. Публиковать median/p95/p99, CPU-seconds, разброс/доверительный интервал и ошибки/корректность KV.
5. Оставить 2048 как целевой пользовательский сценарий. Добавить 16K/32K как масштабные точки, но не заменять ими проверку обещанных 7–15% на 2048.

При 86 MiB и 17.88 Gbit/s идеализированное wire-время около 40.3 ms. Это ориентир, не прогноз: 17.88 измерено отдельным Mac→Spark bulk gate, направление/размеры и GPU extraction отличаются от Spark→Mac KV. Нельзя приписать всё отличие от 80 ms драйверу.

KV порядка 40 KiB/token даст около 1.25 GiB на 32K, но prefill тоже меняется с контекстом. Рост KV не доказывает автоматически рост его доли в TTFT. Действующая квота 512 MiB на client означает, что такой тест должен стримить bounded windows и освобождать idle registrations; один MR на весь 1.25 GiB будет отвергнут. Квоту не снимать ради теста.

## Драйверные проверки этой работы и граница подтверждения

- В этой работе hot-update успешно установил **0.390**. На нём runtime gate подтвердил отказ опасному raw Exec, отказ слишком большой регистрации до pin, MR 1 B / 16385 B с offset / 2 MiB / 64 MiB и возврат charged bytes к baseline.
- Новый Metal contract прошёл host tests с реальным GPU и mock verbs, а затем отдельный **реальный GPU → NIC RC loopback → GPU**, 64 × 4096 B, MTU4096, с slot reuse и close=EBUSY при активной работе.
- CQ-event прогон: 100 запросов / 200 успешных CQE, lost=0. Hybrid: median 71 us, max 88 us в одном прогоне. Power: median 424 us, p95 51.366 ms, p99 51.518 ms; IRQ EQEs=0, timer EQEs=48. **Power-режим не принят как low-latency**; длинный backstop/event rearm требует отдельного исправления и теста.
- Peer Metal gate: Mac→Spark 32 × 1 MiB, 17.88 Gbit/s; reverse Spark→Metal и 4 MiB indirect reverse — PASS, GPU mismatches=0. Это не сквозной inference benchmark и не доказательство Spark GPU zero-copy.
- Во время продолжения обнаружены параллельные изменения тех же исходников и обновления DEXT. Последний read-only snapshot: активна **0.396**, epoch=155906052471416, quarantine=0, pinned_charge=0, irq_eqes=0, timer_eqes=10079, irq_proven=0. Результаты разных моментов не выдаются за единый version-pinned release gate.
- Второго Mac нет. Другие M-чипы, destructive fatal/reset/unplug и доставка event без таймерной помощи не сертифицированы этой проверкой.
