## 1. Что мерялось

Две машины поднимают один GGUF и работают как кластер:

| Режим | Префилл | Декод |
|---|---|---|
| **disagg** (дизагрегация) | Spark (CUDA) | Mac Studio (Metal), KV-кэш хендофится Spark→Mac |
| **split** (layer-split 55/45) | обе машины | обе машины, активации ходят по RPC на каждый токен |

Транспорты: **RDMA (40G RoCEv2)** vs **TCP (10GbE control-path)** — фолбэк того же RPC-канала.

Метрики на каждую точку (медианы): префилл tok/s, декод tok/s, TTFT (время до 1 токена), CPU% llama-server (Mac) и rpc-server (Spark).

Модели:
- `Qwen3.8-27B-UD-Q4_K_XL` (17.9 GB)
- `Qwen3.6-35B-A3B-MTP-UD-Q4_K_XL` (22.8 GB, MoE 3B active)

Свип контекстов: 512 → 65536 (8 окон). Репы: 3 (≤8K), 2 (16–32K), 1 (65K).

## 2. Топология и bring-up

```
Mac Studio M2 Ultra                         DGX Spark (aarch64, 20C, 121 GB)
  ConnectX-4 Lx (MelonDMA DEXT)     40G DAC ⇄  ConnectX-7 rocep1s0f1
  RoCEv2 GID ::ffff:192.168.200.1             RoCEv2 GID ::ffff:192.168.200.2
  ────────────────── RDMA data path (UDP/4791) ──────────────────
Mac en0 192.168.100.1                   10GbE ⇄  Spark enP7s7 192.168.100.2
  ────────────────── TCP control / fallback data path ────────────
```

Рабочий рецепт (выводится перебором из замеров, `spark-rpc` = 192.168.100.2 в `/etc/hosts`):

```bash
# Mac: llama-server (подписан userclient-access), клиент RPC
export MELONDMA_LOCAL_IP=192.168.200.1
export MELONDMA_LOCAL_MAC=98:03:9b:80:6a:94
export MELONDMA_REMOTE_MAC=4c:bb:47:7d:a1:a5   # Spark rocep1s0f1
export GGML_RDMA_GID=0                          # Mac GID index (::ffff:192.168.200.1)
./build/bin/llama-server -m <model> --rpc spark-rpc:50052 \
  --device MTL0 --prefill-device RPC0 -c 65536 ...   # disagg
  # или --device MTL0,RPC0 --split-mode layer --tensor-split 55,45   # split

# Spark: rpc-server
export GGML_RDMA_DEV=rocep1s0f1 GGML_RDMA_GID=3
./build/bin/rpc-server -H 192.168.100.2 -p 50052 -c

# TCP-фолбэк (для сравнения): на Mac добавить GGML_RPC_DISABLE_RDMA=1
```

Билды: обе стороны пересобраны с `GGML_RPC_RDMA=ON` (Mac — через `-DMELONDMA_DEXT_DIR=.../dev/src/dext`, Spark — синхронизирован `ggml/src/ggml-rpc/*` с Mac, т.к. wire-протокол разошёлся: caps 24→32 байта). Mac `llama-server` подписан `com.apple.developer.driverkit.userclient-access` (+ `disable-library-validation`).

## 3. KV-хендофф идёт по RDMA (RoCEv2) — доказательства

### 3.1 Счётчики NIC (byte-точные)

Один disagg-прогон (модель + 1 префилл 4044 ток.), Spark `enp1s0f1np1`:

| Счётчик | Δ за прогон | Значение |
|---|---|---|
| `rx_vport_rdma_unicast_bytes` | **+16.37 GiB** | модель Mac→Spark по RDMA (веса 17.9 GB) |
| `tx_vport_rdma_unicast_bytes` | **+539.6 MiB** | KV-хендофф Spark→Mac по RDMA (≈2×284 MiB KV) |

Это NIC-счётчики **RDMA unicast**, не netdev (netdev-счётчики того же порта почти не растут — обычный Ethernet отдельно). ΔTX ≈ 2× размер KV, т.к. KV уходит **дважды**: чанками-префетчем *во время* префилла + финальным `get(net)`.

### 3.2 RoCEv2 (не v1)

- Spark при коннекте: `RDMA probed: dev=rocep1s0f1 gid=3 RoCEv2 qpn=…` — транспорт явно выбрал GID-тип **RoCEv2** (в коде приоритет `IBV_GID_TYPE_ROCE_V2` над v1).
- Используемый GID `::ffff:192.168.200.2` — IPv4-mapped (=RoCEv2-адресация). RoCEv1 был бы `fe80::4ebb:47ff:fe7d:a1a5` (MAC-derived) — он в таблице есть, но не выбран.
- Обе стороны: `RDMA connection active`, MTU 4096.

### 3.3 Стриминг хендоффа — `get(net)` почти не растёт с контекстом

Ожидание для bulk-хендоффа: `get(net)` растёт линейно с KV. Факт:

**Qwen3.8-27B (disagg/rdma):**

| токенов | KV | get(net) | set(local) |
|---|---|---|---|
| 4 400 | 295 MiB | 68 ms | 6 ms |
| 9 000 | 449 MiB | 71 ms | 10 ms |
| 18 200 | 754 MiB | 108 ms | 23 ms |
| 36 600 | 1 365 MiB | 121 ms | 41 ms |
| 75 300 | 2 651 MiB | 176 ms | 88 ms |

**Qwen3.6-35B-A3B (disagg/rdma):**

| токенов | KV | get(net) | set(local) |
|---|---|---|---|
| 4 400 | 108 MiB | 30 ms | 4 ms |
| 9 000 | 156 MiB | 32 ms | 5 ms |
| 18 200 | 252 MiB | 37 ms | 9 ms |
| 36 700 | 445 MiB | 44 ms | 18 ms |
| 75 400 | 846 MiB | 69 ms | 38 ms |

Эффективная скорость финального get растёт **выше физики линка**: 2 651 MiB / 176 ms ≈ **15 GB/s** при потолке 40G-линка ~3–5 GB/s. Это возможно только если бОльшая часть KV **уже закеширована на Mac** — т.е. KV пришёл чанками во время префилла (стриминг-хендофф работает), а финальный `get(net)` читает уже локальный кэш.

## 5. CPU-накладные (суть замера)

| Режим | mac_cpu RDMA | mac_cpu TCP | spark_cpu RDMA | spark_cpu TCP |
|---|---|---|---|---|
| disagg (декод-нода Mac) | **~48%** | **~3%** | ~100% | ~92% |
| split (большие ctx) | ~4% (17.8→4.5) | ~1.4–3.3% | ~100% | ~20–40% |

Главный вывод: в disagg Mac жжёт **~45% ядра на busy-poll CQ** в RDMA-режиме — транспорт `rdma_recv` крутит `ibv_poll_cq` в цикле (нет комплейшн-ченнела/epoll). TCP при этом почти бесплатен (ядро). Это цена zero-copy: выигрыш TTFT до −10.7% на 65K оплачивается пол-ядром на приёмнике.

В split Mac-нода почти не грузит CPU (декод распределён, KV сплитован), но decode **медленнее на RDMA** (активации — мелкие сообщения, busy-poll на каждое дороже батчированного TCP-стрима).

## 6. Выводы

1. **disagg + RDMA — правильный режим для длинных контекстов.** Префилл +2–12% (растёт с ctx), TTFT до −10.7% на 65K. Причина: KV-кэш стримится по RDMA во время префилла, TCP упирается в 10GbE на bulk-переносе.
2. **split — RDMA не даёт выигрыша.** Decode до −13% на 35B-A3B: активации = мелкие сообщения, где busy-poll RDMA медленнее TCP. Split вообще slow-path (decode 7–14 tok/s vs 24–68 в disagg) — его смысл только «модель не влезает в одну машину», не скорость.
3. **RDMA-транспорт оверхед = busy-poll.** ~45% ядра на Mac в disagg. Возможное улучшение: completion-channel (kqueue/fd) + epoll вместо spin-poll — должно убрать CPU без потери bandwidth.
4. **Стриминг-хендофф работает**, но финальный `get(net)` читает KV повторно (~2× передача): префетч-кэш не доедается финальной сериализацией `state_seq_get_data`. На TTFT влияет слабо (~0.2%), но оптимизируемо.

## 7. Известные артефакты/оговорки

- Mac-нода в RDMA busy-poll даёт стабильный mac_cpu ~48% в disagg — это замеряемая, а не шум, величина.
- `spark_cpu ~0%` в паре строк (35B disagg 512, split 1024) — артефакт сэмплинга `ps` до старта обработки; игнорировать.
- MTU 4096 (RoCE), линк ACTIVE с обеих сторон, 0 CQE-ошибок за весь прогон.
- DEXT собран `MLX_DEBUG=0`: datapath (recv/CQ-poll) в системный лог НЕ пишется (намеренно). Видимость recv — только через NIC-счётчики (`ethtool -S … | grep rdma`) и логи llama.cpp (`RDMA connection active`, `GGML_RDMA_STATS`).
